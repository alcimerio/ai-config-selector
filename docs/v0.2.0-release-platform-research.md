# v0.2.0 release-platform research

Research date: 2026-08-07

This note records the current first-party platform facts that affect issue #45's
release contract. It is not evidence that any repository setting, credential,
workflow run, Release, asset, or attestation currently exists or has passed.

## Immutable GitHub Releases and Release assets

- GitHub defines an immutable Release as one whose attached assets and associated
  Git tag cannot change after publication. The tag is locked to its commit and
  cannot be moved or deleted while the Release exists, and attached assets cannot
  be modified or deleted. If the Release is deleted, its tag can then be deleted,
  but the same tag name cannot be reused. The protection also covers repository
  deletion and recreation under the same name. GitHub automatically creates a
  release attestation containing the tag, commit SHA, and Release assets.
  [GitHub: Immutable releases](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/supply-chain-security/immutable-releases)
- GitHub recommends creating the Release as a draft, attaching all assets, and
  only then publishing it. This ordering is necessary because publication is the
  transition that makes the assets and tag immutable. A published immutable
  Release still permits edits to its title and release notes, so immutability must
  not be described as freezing every field in the Release record.
  [GitHub: Immutable releases](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/supply-chain-security/immutable-releases),
  [GitHub: Managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
- Enabling the repository or organization setting affects future Releases only.
  The setting therefore has to be enabled before v0.2.0 is published; enabling it
  later would not retroactively protect v0.2.0.
  [GitHub: Preventing changes to your releases](https://docs.github.com/en/enterprise-cloud@latest/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes)
- `gh release verify v0.2.0` verifies the Release attestation, while
  `gh release verify-asset v0.2.0 PATH` verifies that a local file exactly matches
  an attached asset. GitHub's on-demand source-code zip and tar archives cannot be
  verified with `verify-asset`; they are not stored Release assets. Release asset
  API responses also expose an asset digest, currently represented as
  `sha256:...`.
  [GitHub: Verifying the integrity of a release](https://docs.github.com/en/enterprise-cloud@latest/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity),
  [GitHub CLI: `gh release verify`](https://cli.github.com/manual/gh_release_verify),
  [GitHub REST API: Release assets](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28)

Contract consequence: stage and validate the exact six-file v0.2.0 Release
Artifact Set in a draft, publish once, then require both an immutable Release
verification and exact public asset-name, size, and digest reconciliation. Never
replace an asset or move/reuse the tag to repair a published defect.

## Protected environments and reviewers

- A job that references a protected environment must satisfy its deployment
  protection rules before it proceeds. Environment secrets are not available to
  the job until a required reviewer approves it.
  [GitHub: Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- An environment may list up to six required users or teams, but approval from
  only one listed reviewer is required. This is one-of-many approval, not an
  N-of-M quorum. Reviewers need at least read access to the repository.
  [GitHub: Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- Preventing self-review is a separate option. When enabled, the actor who
  initiated the deployment cannot approve it even if that actor is a configured
  reviewer. Administrators can bypass protection rules by default, but the
  environment can be configured to disallow administrator bypass.
  [GitHub: Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- On GitHub Free, Pro, and Team, required reviewers are available only for public
  repositories. This plan restriction must be checked rather than inferred from
  the mere availability of environments or environment secrets.
  [GitHub: Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

Contract consequence: the `release` environment should have at least one
required reviewer, self-review prevention enabled, and administrator bypass
disabled if the approval is intended to be unskippable. Store the App credentials
at environment scope so the protected jobs cannot read them before approval.

## GitHub App installation tokens and permission boundaries

- GitHub Apps have no permissions by default, and GitHub recommends requesting
  the minimum permissions required. Repository, organization, and account
  permissions are separate categories. The success of an installation-token API
  request depends on the App installation's granted permissions.
  [GitHub: Choosing permissions for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)
- An installation access token is minted by authenticating the App with a JWT.
  It expires after one hour. The token request can narrow access to selected
  repositories and to a subset of the App's installed permissions, but it cannot
  grant a repository or permission that the installation does not already have.
  If the request omits those restrictions, the token receives all repositories
  and permissions granted to the installation.
  [GitHub: Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)
- Creating or updating repository rulesets requires repository
  `Administration: write`. Reading a specific ruleset nominally requires only
  `Metadata: read`, but GitHub omits its `bypass_actors` unless the caller has
  write access to the ruleset. Therefore an exact check of the authorized bypass
  actor needs the stronger policy authority.
  [GitHub REST API: Repository rulesets](https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28)
- Creating and updating a Release requires repository `Contents: write`; release
  asset update and deletion also require `Contents: write`.
  [GitHub REST API: Releases](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28),
  [GitHub REST API: Release assets](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28)

Contract consequence: using one environment-protected App installation with
`Administration: write` to verify or restore policy and a different installation
with `Contents: write` to stage and publish the Release is a project
least-privilege design, not a GitHub platform requirement. It ensures no single
installation token combines policy mutation and publication authority. Each token
request should also be narrowed to this repository and only the permissions needed
by that job. The token value, App private key, JWT, and authenticated response
bodies are never release evidence.

## Tag rulesets and bypass actors

- Rulesets can target tags using `fnmatch` patterns. Multiple rulesets targeting
  the same tag are aggregated, so a less restrictive ruleset does not cancel a
  stricter one.
  [GitHub: About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets),
  [GitHub: Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)
- `Restrict creations`, `Restrict updates`, and `Restrict deletions` mean that
  only configured bypass actors can respectively create, update, or delete a
  matching tag.
  [GitHub: Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- The REST representation supports `target: tag`, `User` bypass actors, and
  `always` bypass mode. It also makes creation, update, and deletion independent
  rule types. A ruleset must be `active` to enforce its rules.
  [GitHub REST API: Repository rulesets](https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28)
- A specific ruleset response includes `bypass_actors` only when the caller has
  write access to the ruleset. A successful lower-privilege read is therefore not
  evidence that the bypass list is empty or correct.
  [GitHub REST API: Repository rulesets](https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28)

Contract consequence: for `refs/tags/v*`, keep one active ruleset that restricts
updates and deletions with no bypass actors, and a separate active creation
ruleset whose sole bypass entry is the exact authorized `User` in `always` mode.
The split permits one human-owned canonical creation while making later movement
or deletion unavailable even to that creator. Verify the complete rulesets with
the policy App's write authority; do not treat a metadata-only response as proof.

## Artifact attestations and build provenance

- GitHub Actions artifact attestations establish where and how a binary or other
  artifact was built. For a binary, GitHub's current example uses
  `actions/attest@v4` with workflow permissions `id-token: write`,
  `contents: read`, and `attestations: write`, and passes the artifact through
  `subject-path`.
  [GitHub: Using artifact attestations](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- For public repositories, GitHub uses the Sigstore Public Good Instance and an
  immutable public transparency log. An artifact attestation alone provides
  SLSA v1.0 Build Level 2. GitHub explicitly warns that generating an attestation
  has no security benefit unless a consumer verifies it, and that provenance is
  not a guarantee that the artifact is safe; it links the artifact to the source
  and build instructions that produced it.
  [GitHub: Artifact attestations](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/security/artifact-attestations)
- `gh attestation verify FILE --repo OWNER/REPOSITORY` verifies the artifact's
  integrity and SLSA provenance against an expected repository identity. The CLI
  recommends narrowing the signer further with `--signer-workflow` or an exact
  certificate identity; it can also constrain the source ref and source digest.
  The default predicate type is SLSA provenance v1.
  [GitHub CLI: `gh attestation verify`](https://cli.github.com/manual/gh_attestation_verify)
- The automatic immutable-Release attestation covers the published Release's tag,
  commit, and assets. Actions build-provenance attestations describe how specific
  artifact bytes were built. They are complementary and neither substitutes for
  the other or for an independent SHA-256 comparison.
  [GitHub: Immutable releases](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/supply-chain-security/immutable-releases),
  [GitHub: Artifact attestations](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/security/artifact-attestations)

Contract consequence: generate build-provenance attestations for each of the four
archives and `SHA256SUMS`, then verify every downloaded file against this exact
repository and the expected release workflow/source identity. Separately verify
the immutable Release and each stored Release asset. Attestation success must not
be described as malware review, code quality, Apple identity, notarization, or
Gatekeeper approval.

## macOS Gatekeeper for unsigned and unnotarized binaries

- Under default macOS policy, Gatekeeper checks downloaded software for an
  identified developer, Apple notarization, integrity, and known malicious
  content. Apple says that outside-App-Store software is checked for a Developer
  ID signature and, by default on macOS Catalina and later, notarization.
  [Apple: Safely open apps on your Mac](https://support.apple.com/en-us/102445),
  [Apple Platform Security: Gatekeeper and runtime protection](https://support.apple.com/guide/security/sec5599b66df/web)
- When the developer cannot be verified or the software is not notarized, macOS
  may warn that the developer cannot be verified or that Apple cannot check the
  software for malicious content. A user who independently trusts the software
  may attempt to open it and then choose **Open Anyway** in Privacy & Security,
  creating a local exception. Managed-device policy may make that option
  unavailable. Malware, revocation, damage, and tampering alerts are different
  conditions and may remain blocking.
  [Apple: Safely open apps on your Mac](https://support.apple.com/en-us/102445)
- Gatekeeper assessment depends on provenance and quarantine. Apple's testing
  guidance says downloading through a mechanism that quarantines the software is
  necessary to trigger the first-open Gatekeeper check. Consequently, the exact
  user-visible result for a command-line executable can vary with the download
  path, preserved quarantine attributes, OS version, prior local exception, and
  device-management policy; the contract should not promise one exact dialog.
  [Apple: Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html),
  [Apple Platform Security: Gatekeeper and runtime protection](https://support.apple.com/guide/security/sec5599b66df/web)
- Apple describes notarization as an automated malicious-content and code-signing
  check that produces a ticket Gatekeeper can consume; it is not App Review.
  Developer ID signing establishes an Apple-recognized developer identity.
  A project SHA-256 checksum or GitHub attestation supplies neither property.
  [Apple: Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution),
  [Apple: Signing your apps for Gatekeeper](https://developer.apple.com/developer-id/)

Contract consequence: state plainly that the v0.2.0 macOS archives and binaries
are unsigned and unnotarized. They do not have Apple Developer ID identity,
Apple notarization, Apple malware-review evidence, or default Gatekeeper trust.
Some users may encounter a warning or block and must make an explicit,
user-controlled trust decision where host policy permits; managed hosts may
prohibit it. Document no command that disables Gatekeeper or strips quarantine as
a supported installation step. Checksums and GitHub attestations verify different
integrity and provenance properties and do not bypass this Apple trust boundary.
