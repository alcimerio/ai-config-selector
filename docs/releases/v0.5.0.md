# ACS v0.5.0

ACS v0.5.0 adds the Profile lifecycle, contained Codex and Devin capabilities,
and explicit stable-release updating described below. It supports macOS 26 on
Apple Silicon (`darwin/arm64`) only. The immutable v0.4.0 Intel artifact and its
historical evidence are unchanged; they do not extend Intel support to v0.5.0.

## Profiles, history, and recovery

Compared with v0.4.0, v0.5.0 adds passive Profile listing,
inspection, validation, and host diagnostics; confirmed edit, clone, rename,
and delete operations; declarative Profile creation; revision-bound repository
transactions; and explicit interruption recovery.

Profile v3 provides common Skills and workspace authority shared by the Devin
and Codex overlays. Legacy Profiles remain readable and migrate only through an
explicit command. Portable exchange transfers sanitized logical intent with
explicit local bindings; it does not transfer local files, credentials,
history, Sessions, or readiness evidence. Bounded Profile history helps with
supported configuration rollback but is not a machine backup.

Durable Session commands list, inspect, and conservatively recover lifecycle
records. Recovery requires proof that ownership has settled; it never treats a
process lookup or elapsed time as cleanup proof and has no force-delete path.

## Contained Devin and Codex operation

ACS uses one fail-closed contained-process lifecycle for the existing Devin
launcher, the fixed sandbox shell, interactive Codex, and literal-argument
generic commands. Effective-capability explanation reports sanitized authority
without exposing generated policies or private paths.

Interactive Codex uses the checksum-locked supported CLI and isolated named
ChatGPT authentication instead of ambient Codex credentials. Named identities
are stored separately in the macOS Keychain. ACS does not import global Codex
authentication, accept API-key identities, expose arbitrary target arguments,
or provide a less-restricted fallback.

Profiles can select bounded filesystem and executable grants, common
instruction references, scoped environment references, and reference-only
local STDIO MCP servers. Devin projects selected instructions as ACS-managed
always-on rules. Codex retains the common selections but does not activate them
as ACS-managed rules. Environment values are resolved at launch and are not
persisted in Profiles, exchange files, or history. A selected secret can be
read by the target, its local MCP servers, and descendants; it is not isolated
per server. MCP argv can resolve only from selected path references or selected
non-secret environment references.

MCP tool filtering is target behavior, not an ACS containment guarantee. ACS
does not manage remote MCP, plugins, hooks, agents, arbitrary target settings,
or destination-specific network policy. Target-owned project content can still
be discovered within the selected workspace.

## Installation and update

The v0.5.0 release installer is an unsigned and unnotarized Apple Silicon
installer. It verifies the selected archive against `SHA256SUMS`, checks
the embedded version and archive structure, refuses to overwrite an existing
`acs` file, needs no `sudo`, and does not edit shell startup files.

Published v0.4.0 has no `acs update` command. Its users bootstrap v0.5.0 by
downloading and inspecting the release-specific v0.5.0 installer, then
installing into a new empty user-owned direct directory. They
must retain the previous executable, back up quiescent Profile files, verify
the new executable explicitly, and deliberately select it with `PATH`. The
[migration guide](https://github.com/alcimerio/ai-config-selector/blob/v0.5.0/docs/release-migration-guide.md)
and [manual recovery guide](https://github.com/alcimerio/ai-config-selector/blob/v0.5.0/docs/manual-upgrade-recovery.md)
keep binary selection,
Profile migration, data recovery, and rollback as separate decisions.
Direct Profile-file copies exclude history, Skills, Sessions, target state,
transaction evidence, and Keychain credentials; they are not an automatic
restore or data-downgrade mechanism.

After v0.5.0 is installed, `acs update --check` checks published stable release
metadata without downloading an archive or modifying user data. `acs update`
selects the latest published stable release, and
`acs update vMAJOR.MINOR.PATCH` selects a published stable version. The updater
can explicitly reinstall or downgrade a selected published version. It accepts
only its supported direct, user-owned regular-file layout and replaces
only the running ACS executable after release-asset verification. It does not
migrate or downgrade Profiles, identities, history, or Sessions.

Binary rollback does not downgrade stored data. v0.4.0 cannot safely own the
newer formats added after that release, so retain a compatible v0.5.0 binary for
inspection and supported recovery after any newer-state write.

## Platform, integrity, and trust boundary

The release target is macOS 26 Apple Silicon (`darwin/arm64`) with the system
Seatbelt backend. Linux compilation remains a non-blocking portability
observation, and the historical v0.4.0 Intel asset does not extend Intel support
to v0.5.0. ACS is not an egress firewall and does not make target output or
third-party services trustworthy.

v0.5.0 is unsigned and unnotarized; it has no Apple Developer ID signature or
notarization ticket. SHA-256 checksums prove byte identity relative to a trusted
manifest, and GitHub build-provenance attestations provide separate origin
evidence. Neither is Apple approval, notarization, malware review, or a promise
that Gatekeeper will accept the archive. Users must not remove quarantine,
disable Gatekeeper, ad-hoc sign the binary, or weaken Seatbelt to make it run.

## Release evidence and daily-use boundary

The release workflow builds one candidate, installs and exercises those exact
bytes on native macOS 26 Apple Silicon, attests the archive and manifest, and
publishes the same bytes.

Release publication and the week-long daily-use observation with Devin and
Codex in two real projects are separate evidence categories. CI, exact-artifact
validation, and release publication do not establish elapsed daily use, hosted
provider experience, or real-account behavior. Those claims require their own
sanitized observation record.
